## 1. 要做什麼（與明確不做什麼）

在 TungsAcu-DB 加一層**互動人體地圖**，**純導航用途**：讓使用者「選部位 → 在部位圖上找穴位 → 進該穴內容」。對標參考站 **Philosopher Atlas**（https://philosopheratlas.chroniclecore.com/）的「靜態網站 ＋ 資料即檔案（JSON）＋ 瀏覽器端互動」模式。**目標公開**。

**明確不做（NON-GOALS，違反即跑偏）**：
- 地圖**不**承載治療、對針、詳細筆記等內容——那些留在既有的穴位頁。地圖只負責「選區域、找穴位、連過去」。
- **不**追求解剖級精準座標（顥軒明示：位置不用非常精準；只有手指腳趾等密集區要夠清楚不混淆）。
- Phase 1 **不**順手把穴位頁也搬成靜態、**不**做未要求的功能（YAGNI，見 core.md 第 3.8 條「簡潔優先」）。

---

## 2. 架構決策（已定）

- **靜態／JS 前端**，部署目標 **Cloudflare Pages**（免費）。**不用 Streamlit** 做地圖：動畫互動是 JS 前端主場、Streamlit 死穴；公開取向要載入快、能被搜尋引擎索引。
- 這張地圖是董氏資料庫**日後整站搬靜態的第一塊**；現階段與既有 Streamlit app 並存。
- **資料即檔案**：座標與部位資料存成可版本控管、可用編輯器/表單校對的 JSON/CSV（延續顥軒「資料與程式分離、CSV 可手改」的既有原則）。

## 3. 使用者體驗（已定）

**下鑽三層**：
1. **全身層**：一張抽象線繪人體，各部位標**總穴位數**（如參考站世界地圖各區標數字）。資料現成——由 `data/部位表.csv`（13 部位）× `data/穴位表.csv`（216 穴，含部位代碼）即可算出每部位穴數。
2. **部位層**：hover 部位 → 亮起/放大；點進去 → 放大該部位底圖（如手掌），圖上以**紅點**標出該部位所有穴位。
3. **穴位層**：hover 紅點 → **顯示穴名**；點紅點 → 見 §4 側欄。

**密集區（手指/腳趾）不卡的解法（已定）**：
- **最近點感應（Voronoi / nearest-point）**：hover 的感應範圍是每個點周圍「最靠近它的一整塊」，使用者**不需精準對準**小圓點，滑到誰的地盤就顯示誰。這是讓密集區可用的關鍵，務必實作，不要用「只有小圓點本身可 hover」的天真作法。
- **底圖可縮放**：太密處讓使用者放大，點自然散開。（注意：現有 production 底圖是 PNG 點陣，放大會失真；若要無損放大需 SVG，見 §7 待確認項。Voronoi 感應與底圖是不是向量無關，PNG 也能做。）
- 結論：**不需**被迫加深下鑽層級；hover 顯示穴名（此為顥軒選定的方案 B）＋ 最近點感應即可。

## 4. 點下紅點的去向：側欄預覽（已定，取代原本的「甲/乙」二選一）

hover/點紅點時，在地圖旁**跳出側欄**，直接顯示該穴重點：**穴名、穴號、取穴定位、主治關鍵字**——這些欄位 `data/穴位表.csv` 都有，前端讀出即可，**不必新建整套靜態穴位頁**。側欄底部放「看完整內容 →」連到既有穴位頁。

- 好處：地圖本身就有用、不必每次跳走、不吃 Streamlit 冷啟動；範圍幾乎沒變大（只渲染已有的 CSV 欄位）；完整內容仍走原頁面，符合「治療/對針留在原頁」。
- 「看完整 →」的連結目標：既有 Streamlit app **支援深連結**（`app.py` 已用 `st.query_params`，見 728/777/797/803 行），可帶穴位參數直接開到該穴。Phase 1 就連到 Streamlit；日後整站搬靜態時，此連結自然改指靜態穴位頁。

## 5. 三階段路線圖

### Phase 1 — 地圖引擎垂直切片（先做這個）
**目標**：做出一個能動、能 hover、能點、能公開的最小地圖，驗證整體體驗值得做。
**內容**：
- 全身層 →（一個）部位層 →（紅點）hover 顯示穴名 → 側欄預覽 → 「看完整 →」連回 Streamlit。
- **定義座標資料格式**（見 §6），這是 Phase 1 的核心交付，之後所有部位都照這格式填。
- **用一張已合格的 production 底圖**（見 §7 現況）＋**少量手動擺放的示範座標點**做出可動原型。**刻意與製圖進度解耦**：前端不空等座標全標完；先證明引擎與資料格式，再把真座標陸續灌進來。
**驗收**：靜態部署（Cloudflare Pages 或先本機），至少一個部位可下鑽、紅點可 hover 出名、側欄顯示 CSV 四欄、連結可深連到對應穴位頁。

### Phase 2 — 補齊各部位座標與底圖
把 13 部位的抽象底圖與穴位座標補齊，逐一灌進 Phase 1 的資料格式。位置放寬、可手動擺點。**此為獨立的資料生產工作，與顥軒的製圖/套皮專案協調**（見 §7），不要在 Phase 1 展開。

### Phase 3 — 症狀反查亮穴（真正的臨床殺手級功能）
加篩選：**選一個症狀 / 主治關鍵字 → 全身圖上相關穴位亮起、其餘淡化**（即參考站「拉時間軸只亮某年那批人」的同一手法）。資料現成——`穴位表.csv` 每穴有「主治關鍵字」，另有 `症狀映射表.csv`、`症狀治療.csv`。需把主治標籤帶進地圖資料、加一套篩選 UI。**範圍較大，排在最後，不要提前混進 Phase 1。**

## 6. 座標資料格式（Phase 1 要定案的交付）

地圖需要「每個部位一份、內含該部位所有穴位在底圖上的位置」。建議格式（實作者可微調，但精神照此）：

```json
{
  "region_code": "一一",
  "region": "一一部位",
  "zone": "手指穴位",
  "base_image": "image-library/production/<檔名>.png",
  "image_size": [寬, 高],
  "view": "palmar | dorsal",
  "points": [
    { "code": "11.01", "name": "大間穴", "x": 0.42, "y": 0.31 }
  ]
}
```

- **x/y 建議用「相對比例（0–1）」而非絕對像素**，這樣換底圖尺寸不會壞掉。
- `code`/`name` 要對得回 `穴位表.csv` 的「穴號」「穴名」，側欄才能撈到該穴的取穴定位與主治關鍵字。
- 這份 JSON 就是日後「補座標」的填空對象；也可接表單式編輯（參考站用 Sveltia CMS 讓非工程師改，衍生欄位鎖定不可手填——值得日後借鏡）。
